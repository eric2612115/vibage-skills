Impl loop for the review-record schema hardening described in
`docs/superpowers/specs/2026-07-26-review-record-schema-hardening-design.md`, frozen after eight
plan-loop rounds.

Three reviews across three distinct contexts. Reviewer A checked the code against each spec rule
rather than against the tests, since the tests were written by the implementing agent. Reviewer B
ran the closed-defect list and, equally, a control set of legitimate constructs, because an
implementation that rejects everything would satisfy the first half alone. Reviewer C re-ran the
fifteen attacks demonstrated during the design work, the legitimate-record control, the corpus, and
the four scanning rules earlier dry runs had got wrong.

One defect was found and fixed inside the loop: the shipped case 5 fixture placed its embedded `---`
before two of reviewer B's required fields, so against the pre-change code the record failed for
missing fields rather than for the truncation the case exists to pin. Checked against `58c553a`: the
old layout printed `REVIEW_RECORD_FAIL`, the corrected layout prints `REVIEW_RECORD_OK` with the
failing reviewer invisible to the parser, which is the false green case 5 is supposed to guard.
Fixed in `abe5941`.

Two non-blocking deviations are recorded rather than fixed. After a duplicate `blocking` key, later
list items still append to the first list; the record fails on the duplicate either way, and the
spec itself notes that the keep-first pin only affects which value appears in an error message. A
line carrying a control character can also be reported as unrecognised, producing two messages; the
spec does not forbid it and the outcome is fail-closed.

`REVIEW_RECORD_OK` is not review quality. A single reviewer would not have been sufficient under
this package's own rules, and the model mix here is disclosure, not a gate — the gated axis is the
three distinct contexts.
